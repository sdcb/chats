# Chats 产品愿景

Chats 计划把 Code Interpreter 从“会话级临时容器”逐步演进为可治理、可跨会话复用的个人运行环境，并补齐 Agent 在需求澄清、断线恢复和多轮文件处理方面的基础能力。本页记录长期产品愿景和需要继续确定的设计问题，不绑定具体版本，也不代表功能已经交付。

## 永久 Docker 与资源治理

- Docker 从当前 Chat 级 session 演进为由用户拥有、可跨会话复用的持久化 Docker；现有临时会话级 Docker 继续保留，并拥有独立的生命周期和清理策略。
- 用户可以查看自己创建过的 Docker，并在每次聊天中选择允许 Agent 访问哪些 Docker，避免 Agent 默认看到全部运行环境。
- 管理员拥有统一管理入口，可以查看和管理自己的及所有用户创建的 Docker。
- 引入可配置的资源配额，覆盖容器总数、CPU、内存、网络能力，并为后续资源类型预留扩展空间。管理员可以配置用户或自身的配额，但任何配额都不能突破 Docker 主机的物理容量和系统安全边界。
- 团队或项目级 Docker 共享是有价值的后续方向，本阶段暂不纳入范围。

## 独立网站托管、Volume 与网关/DNS

- 支持独立的持久化 volume，使网站代码、上传文件和后端数据库数据不必全部存放在 container 内。
- 定义抽象的网站发布契约，至少描述域名、入口端口、协议、路由和容器目标。
- 首批适配自有 Caddy2 网关，探索通过 API 或等价机制自动维护反向代理配置；同时保留人工确认和失败回滚的能力。
- 首批适配阿里云 DNS 和 Cloudflare DNS，逐步打通子域名、DNS 记录、端口映射、Caddy2 路由和证书流程。
- “用户告诉 AI 要公开访问某个网站”应最终能够转化为可确认的发布计划，但端口、域名所有权和公网暴露边界仍需进一步设计。

## Agent 计划模式、问答与中途插话

- 提供“正常模式”和“计划模式”两个显式模式。正常模式要求 Agent 尽量一次完成任务，计划模式要求 Agent 对不明确的需求主动澄清。
- `Ask question` 始终存在于工具列表中，但不同模式使用不同提示词：正常模式尽量不调用，计划模式在必要时必须调用。
- 一次 Ask question 请求最多承载三项问题及用户答案。前端增加与后端聊天的交互入口，后端收到答案后继续当前 ReAct 循环。
- Agent 执行期间允许用户发送补充消息。消息先排队，在下一次工具调用完成后按顺序注入当前循环，尽量减少对正在进行的工作影响。
- subagent/子代理是后续评估方向，本阶段不实现，也不默认自动启动子代理。

## 有状态的模型文件与图片上下文

- 抽象不同模型提供商的 response/file/image ID 映射，避免多轮对话反复发送 base64 或本地图片 URL。
- 后端记录文件已经上传到哪些提供商、对应的远端 ID、有效期和失效状态；远端文件过期或不可用时检测并回退到本地文件传输。
- 首批验证范围为 DeepSeek 的三种协议，以及 Azure AI Foundry 的 Responses API；其他提供商暂不承诺同等测试覆盖。

## 流式响应和停止状态持久化

- 将运行中的 SSE/流式事件和 stop token 状态持久化到数据库，使页面刷新或短暂断线后仍可恢复 Agent 进度，并可以继续停止正在运行的任务。
- 客户端重新连接时按事件序号补发，避免 Ask question、工具调用和中间输出出现重复或丢失。
- 运行期间保留恢复所需的完整事件；会话完成或失败后保留可配置的短期窗口，再由后台任务定期清理，最终聊天消息、工具结果和用量记录继续按现有模型保存。

## 仍需澄清的问题

- 永久 Docker 的停止、休眠、重启、删除和闲置回收默认策略是什么？用户被禁用或超出配额时，容器与 volume 如何处理？
- 配额按用户、租户、Docker 主机还是多级叠加计算？网络能力需要支持无网络、受限出站、指定域名和完整出站中的哪些等级？是否允许入站端口？
- volume 使用 Docker named volume、宿主机目录还是抽象存储后端？是否需要备份、迁移和独立的磁盘配额统计？
- Caddy2 配置失败、DNS 记录冲突、域名不属于本站或证书签发失败时，是否必须人工确认并回滚？公网发布时由用户指定域名/端口，还是由 Agent 生成候选后确认？
- Ask question 的答案是否永久写入聊天历史，还是仅作为 Agent 控制事件保存？中途插话的顺序、超时和工具调用长时间不返回时的行为如何定义？
- 提供商远端文件过期后的重新上传、费用归属和隐私删除策略是什么？SSE 事件完成后的短期保留时长和清理失败重试策略是什么？

## 规划边界

- 本愿景文档只记录方向，不包含上述功能的实现、API 承诺或数据库迁移。
- 具体接口、权限模型、数据结构、兼容性策略和发布顺序将在设计完成后另行确定。

## 后续演进设想

### 聊天分支浏览与内容按需加载

- 当前聊天只有一个聊天级 `LeafTurnId`。懒加载切换到不包含该 leaf 的 sibling 子树时，当前实现先按目标子树中最深且最新的 leaf 选择默认可见路径。
- 后续可为每个 turn 或分支增加独立的 `LeafTurnId`，使用户返回曾经浏览过的分支时可以恢复该分支上一次选中的后代，而不是重新按最新 leaf 推导。
- 这项持久化模型重构需要重新设计 turn 级 leaf 的更新、删除、复制、分享和数据库迁移方案。
- 思考内容等非当前界面必需的消息内容可进一步改为按需加载，避免历史分支数据在首次打开聊天时被全部传输。
