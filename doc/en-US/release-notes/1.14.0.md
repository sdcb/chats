# Chats 1.14.0 Release Notes

> Release Date: 2026-08-13 (18 non-merge commits since 1.13.0.721)

Chats 1.14.0 focuses on consistent model context, organization-wide preset model groups, administrator user controls, reliable MCP shortcuts, and tool-call compatibility across multiple providers.

## 🧠 User Context Snapshots

Chats now stores the original user text shown in the interface separately from the context actually sent to the model. This prevents historical messages from producing different model input as time, files, or runtime environments change, and improves the likelihood of retaining a stable Prompt Cache prefix.

- `StepContentText.Content` continues to store and display the original user text, while the new `ContextTemplate` stores the model context frozen when the message is created.
- Dynamic information such as the current time, target model, Code Interpreter files, and Docker session is written into the snapshot when the user message is created. Continuing a historical conversation or regenerating a response does not recompute it.
- A user message can use `{{#spans:1,2}} ... {{/spans}}` conditional blocks to render different context for different spans. Spans with identical content are automatically merged and deduplicated.
- Templates consistently use LF line endings. Removing a non-matching conditional block also removes its directive lines, avoiding extra blank lines and unstable context prefixes.
- The original user text replaces `{{USER_CONTENT}}` only after conditional parsing, so template markers, XML, or consecutive line breaks in user content are not interpreted again.
- An empty template automatically falls back to `Content`; existing messages require no backfill or migration.
- Editing a message in place preserves its existing context snapshot. "Edit and send" creates a new message with a fresh time and environment snapshot.
- Context is rendered centrally when converting to a Neutral Message, so providers such as OpenAI and Anthropic do not need separate template implementations.

## 🌐 System Preset Model Groups

- Administrators can mark a preset model group as a system preset, making it visible to every signed-in user.
- System and personal presets appear in the same list, with system presets always ordered before personal presets. A shield icon and `System Preset` tooltip distinguish them.
- The Reset Models dialog in chats also displays the system-preset indicator.
- Regular users can apply and clone system presets, but cannot edit, delete, or reorder them. A clone is always created as the user's own personal preset.
- Administrators continue to manage system presets through the existing preset model group editor. System and personal presets are sorted independently and cannot be moved across scopes.
- Applying a preset rechecks the user's model and MCP permissions. Insufficient permissions return an error instead of relying on potentially stale checks saved while listing presets.
- Default Prompts remain available in this release. Later releases will gradually replace the relevant capabilities with system preset model groups.

## 👤 Administrator User Management

- The user list and editor now include SSO Sub and API Key permission information. Account and sign-in Provider are displayed as read-only fields.
- Administrators can update or clear the Sub of a Keycloak user; duplicate Sub values are rejected.
- Administrators can directly reset a user's password. A new password must be at least eight characters and contain at least three of the following categories: uppercase letters, lowercase letters, digits, and special characters.
- Administrators can prevent a user from using API Keys. Disabling permission does not delete existing keys, but invalidates them immediately. Re-enabling permission restores keys that have not expired or been revoked.
- API Key permission is included in both sign-in token claims and the login response, allowing the frontend to control access directly from login information without an additional permission-status request.
- The API entry in the user avatar menu and the API Keys tab on the Build page are shown only to users with permission. Administrators follow the same restriction.
- Authentication caches are invalidated immediately when an API Key is modified, revoked, or deleted, or when an administrator disables the user or API Key permission, eliminating the previous delay of up to five minutes.

## 🎁 Initial Account Configuration

- Administrators can preassign MCP permissions in an initial account configuration and independently configure shortcuts and user-level custom request headers.
- Initial configurations can determine whether new users may use API Keys. Existing configurations and users remain enabled.
- Configuration matching now follows deterministic precedence: a configuration matching both sign-in type and invitation code wins, followed by invitation-code-only, sign-in-type-only, and unrestricted configurations. Ties are resolved consistently by the most recent update time.
- If an MCP referenced by an initial configuration is later deleted, new-user creation skips that MCP and records a warning without blocking registration or other initial resources.

## 🧩 MCP Management and Tool Naming

- MCP labels are now unique per owner instead of globally unique, allowing different users to create MCP servers with the same label.
- Administrators see only MCP servers they created or that are assigned to them by default, with an option to switch to the complete MCP view. Visibility for regular users is unchanged.
- Different MCP servers can expose tools with the same name. Conflicts receive deterministic aliases based on the MCP ID, which are mapped back to the original server and tool name when invoked.
- Deterministic tool names and stable ordering replace random prefixes, preventing identical chat configurations from producing different tool definitions and context prefixes across requests.
- Selectors, shortcuts, and system instructions append the MCP ID when same-label MCP servers owned by different users need to be distinguished.

## ⚡ MCP Shortcut Reliability

- MCP shortcut buttons in ChatInput now use chat-level REST endpoints: `PUT /api/chat/{chatId}/mcp/{mcpServerId}` to enable an MCP and `DELETE /api/chat/{chatId}/mcp/{mcpServerId}` to disable it.
- A single request updates every tool-call-capable span in the current chat. The frontend no longer submits multiple complete ChatConfig objects concurrently, avoiding partial success, partial failure, and stale-state overwrites.
- Enabling ensures that each target ChatConfig retains at most one association with the MCP. Disabling removes every association with that MCP, including historical duplicates.
- The backend returns the latest complete span list, which the frontend adopts directly. Shortcut operations are locked while a request is running to prevent duplicate requests from rapid clicks.
- Fixes existing duplicate MCP associations causing shortcut errors such as `Duplicate MCP servers are not allowed` or preventing the shortcut from toggling. This fix adds no database constraint and requires no database migration.

## 🔧 Provider and Tool-Call Compatibility

- **Fixes persistence failures from interleaved streaming tool calls**: some OpenAI-compatible providers insert ordinary text between tool-name and argument deltas. Chats now merges tool calls across text segments by their response `Index`, preventing tool-call records with `Name = NULL` from being saved. The fix changes only in-memory aggregation and adds no database access.
- **Fixes multi-turn tool calls in the DeepSeek Messages API**: requests to DeepSeek now omit empty thinking blocks that contain only a signature and no thinking text, preventing subsequent requests from returning HTTP 400 because `redacted_thinking` is unsupported. Thinking blocks with text and their signatures are preserved, and behavior for other Anthropic providers is unchanged.
- **Fixes grouping of parallel Anthropic Messages tool results**: when one assistant message starts multiple `tool_use` calls, the corresponding `tool_result` blocks and attachments are combined into the same immediately following user message, preventing compatible endpoints from reporting missing tool results.

## ⚠️ System Prompt Dynamic Variable Deprecation

- The default system prompt created by a new Chats installation no longer contains the current date. Time and model information have moved to the user context snapshot.
- Chats 1.14.0 retains replacement of `{{CURRENT_DATE}}`, `{{CURRENT_TIME}}`, and `{{MODEL_NAME}}` for compatibility with existing default and custom prompts.
- This release does not migrate or modify existing system prompt data.
- **Chats 1.15 will completely remove these three dynamic variables.** Remove them from custom system prompts before upgrading to 1.15.

## 🔍 Request Trace

- **Fixes incorrect status codes for unhandled inbound exceptions**: Request Trace previously read the default HTTP 200 before ASP.NET Core wrote the final error response. Such records now correctly show HTTP 500 and use 500 when matching status-code filters, ensuring that `5xx` filters do not omit exceptional requests.

## 🔁 Transient Model Request Retries

- Before any content has been sent to the client, text chats retry HTTP 408, 429, 500, 502, 503, and 504 responses, as well as network connection and internal timeout errors, with exponential backoff for up to five retries by default. Requests that have started streaming are not replayed, and image generation does not use this policy.
- The new configuration setting is `Chat:MaxTransientRetries`. The previous `Chat:Retry429Times` setting remains as a compatibility option in 1.14.0 and produces a deprecation warning when used.
- **Chats 1.15 will remove `Chat:Retry429Times`.** Migrate deployment configuration and environment variables to `Chat:MaxTransientRetries` before upgrading to 1.15.

## 🧪 Stability and Tests

- Covers context-template generation, span-conditional rendering, content deduplication, line-ending normalization, invalid templates, and isolation of original user text.
- Covers removal of multi-span conditional blocks without extra blank lines, historical-message fallback, template cloning, and model-message content ordering.
- Adds unit tests for administrator password rules and API Key login claims.
- Adds regression tests for each provider compatibility fix.
- Covers MCP tool-name conflicts, reserved Code Interpreter names, stable aliases, administrator visibility, and disambiguation of same-label MCP instructions.
- Covers idempotent MCP shortcut behavior, including adding missing associations, consolidating duplicates when enabling, and deleting every target association when disabling.
- Adds a regression test for inbound exception status-code recording.
- Adds regression tests for transient model errors, first-output protection, retry counts, image exclusion, configuration compatibility, and `Retry-After` handling.
- Removes Fiddler HTTP dump recordings from provider tests and replaces them with minimal inline JSON/SSE replay fixtures, reducing repository size and eliminating test dependencies on working-directory files.

## ⬆️ Upgrade Notes

- For SQL Server deployments, run: `src/scripts/db-migration/1.14/1.14.0.sql`
- The migration adds nullable `ContextTemplate NVARCHAR(MAX)` to `StepContentText`, `IsSystem` to `ChatPreset`, `ApiKeyEnabled` to `User`, MCP JSON and initial API Key permission fields to `UserInitialConfig`, and changes MCP label uniqueness to be scoped per owner.
- Historical messages are not backfilled with context templates. Existing presets remain personal presets, and existing users are allowed to use API Keys by default.
- Existing system prompts are not modified automatically. Review them and gradually remove `{{CURRENT_DATE}}`, `{{CURRENT_TIME}}`, and `{{MODEL_NAME}}` in preparation for their removal in 1.15.
